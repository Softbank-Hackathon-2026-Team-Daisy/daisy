# PR #19 피드백 반영

기준: 2026-10-01. 엔티티·공통 기반 PR에서 승인된 수정 범위이며 실행 서비스는 별도 브랜치 작업입니다.

- 원인: DaisyException의 details 경로가 없고 낙관적 잠금 예외가 공통 500으로 응답했습니다. 생성자·handler로 안전한 명시 값의 전달을 연결하고 낙관적 잠금을 STATE_CONFLICT 409로 처리했습니다. 원인 미판별 DB 무결성 예외는 INTERNAL을 유지하며 constraint별 변환은 소유 서비스 책임입니다.
- 검증: 실제 application.yml을 읽는 Jackson 슬라이스에서 snake_case·UTC Instant, details 방어 복사·HTTP 전달, 낙관적 잠금/미분류 무결성 구분을 검사했습니다. 기존 비밀값 비노출·요청 ID·매핑 검사를 포함한 13개 테스트와 Spotless·build가 통과했습니다.
- 명세: Jenkins 소유·폴링·plan/apply 분리, source_version_id 선택, map→API digest projection, attempt 0/재사용/호출 실패 구분, SSE 필터·운영 락 해제 방향, 선택 필드 분류와 migration 대조 목록을 갱신했습니다.

## 은현에게 보낼 계약 답변안 — 아직 미게시·미합의

아래 S1~S8은 질문을 다시 나열하는 대신 승환의 권장안을 제시한 것입니다. 은현 동의 후 SPEC/OpenAPI와 #19·#13 답변에 반영합니다. 프론트가 변경할 필드는 소비자에게 함께 공유합니다.

### S1. 목록·프로젝트·빌드·로그·오류 응답

- 목록은 `{items, next_cursor}`로 통일하고 비페이지 목록도 `next_cursor: null`을 반환하는 안입니다. 프로젝트 생성은 Project 단건을 반환하고 manifest는 별도 GET으로 조회합니다. #9의 생성 응답에 manifest를 포함하겠다는 과거 답변과 다른 제안이므로 합의 없이 변경하지 않습니다.
- 빌드 목록에 `source_version_id`를 내보내고 `POST /projects/{id}/deployments`는 그 ID와 target_ids로 선택하게 합니다. 기존 commit/strategy 필드의 호환·제거는 OpenAPI에서 함께 정하고, ID와 commit을 모두 받는 기간에는 같은 프로젝트·commit인지 검증합니다. 같은 commit의 아무 빌드나 자동 선택하지 않습니다.
- DB `source_version.status=succeeded`를 기존 `pipeline.status=success`로 변환합니다. 나머지 상태도 기존 소비자 enum을 대조하고, DB enum을 API에 그대로 노출하지 않습니다.
- 로그 조회의 한 줄은 `seq, at, message`를 기준으로 하고 필요하면 target_id/step/level을 함께 제공합니다. SSE 이벤트의 `ts`와 로그 DTO의 `at`은 용도가 달라 자동으로 한쪽 이름을 바꾸지 않습니다.
- manifest 오류는 기존 오류 봉투의 `details.fields: [{path, message}]`로 제안합니다. 원문 값·비밀값은 제외하고 이 경로 배열은 manifest producer가 생성합니다. 공통 bean validation의 필드명 계약까지 일괄 변경하는 제안은 아닙니다.

### S2. attempt와 단계 표시

- DB는 0..3을 유지하고 A-04의 attempt는 아직 시도하지 않았거나 AI 미호출이면 null, 실제 회차가 있으면 1..3으로 내보내는 안입니다. 클라이언트는 null을 `—`로 표시합니다. 재사용은 인프라가 확인한 reused_script 값으로 구분하고, 0을 임의로 1로 바꾸지 않습니다.
- step/step_state·started_at/duration은 확인한 대상별 이벤트가 있을 때만 제공합니다. 없으면 null 또는 선택 필드 생략으로 명시합니다. 단계 목록이 없음을 `[] = 모든 단계 없음`으로 해석하지 않도록 계약에 씁니다. stale 재plan이 attempt를 올리지 않는 기존 규칙은 유지합니다.

### S3. 사용량 응답

- 상세는 기존 `GET /projects/{id}/ai-usage?deployment_id=...`, 승인 화면 합계는 A-05를 유지합니다. 상세 필드는 at/deployment_id/target_id/step/attempt/tokens/cost_krw/status와 선택 note로 맞추고, title은 별도 중복 필드를 두지 않는 안입니다. 작업 이름은 step에서 표시하며 note는 실제 원본 설명이 있을 때만 제공합니다.
- calls는 실제 확인한 원천 호출 수를 제공합니다. 상세가 페이지화되거나 원본이 누락될 수 있으므로 현재 페이지 행 수로 전체 호출 수를 계산하지 않습니다. 호출별 누락을 0원/재사용으로 해석하지 않습니다.
- 합계와 상세의 중복 합산 방지·합계 전용 보관은 #35에서 정합니다. 환율 숫자는 은현과 함께 확정하고, 미확인 사용량이 있으면 합계도 완전한 총액으로 표시하지 않는 규칙을 API에 명시합니다.

### S4. 다중 승인과 삭제 확인

- 화면은 승인 대기 대상 전체를 한 번에 승인합니다. 요청에는 사용자가 본 `items: [{target_id, approval_id}]`를 보내고, 하나라도 오래됐거나 다른 대상·이미 처리된 승인이면 전체 409로 처리하는 안입니다. 현재 승인 대기 집합과 요청 집합도 대조해 조회 후 새 plan이 생긴 경우 조용히 같이 승인하지 않습니다.
- 삭제가 포함된 plan이 있으면 단일 `confirm_text`에 승인 화면에서 제시한 프로젝트명을 받습니다. 비교할 이름은 pending 생성 시 approval.confirmation_text에 고정하는 안입니다. 프로젝트 이름 변경 등으로 pending 집합의 기대 문구가 달라지면 409로 재조회·재발급을 안내하며 기존 문구를 조용히 바꾸지 않습니다. 이 안은 기존 '대상명' snapshot 설명을 대체하므로 은현 확인 후 DB 사전 의미를 갱신합니다.
- DB 승인 행은 대상별로 유지하고 응답에는 대상별 approval_id 목록을 제공합니다(필드명 `pending_approvals` 제안). 단일 pending_approval의 기존 소비자와 변경 시점을 맞추고, 별도 승인 그룹 테이블을 선제 추가하지 않습니다. 인프라의 단일 APPROVAL_ID 연결은 #35에서 다룹니다.

### S5. 이미지 응답

- DB image_refs는 그대로 둡니다. 단일 서비스는 환경별 image_digest에 실제 digest를 담고, 여러 서비스면 scalar는 null로 두고 서비스별 `images: [{service, image_ref, image_digest}]`를 추가하는 안입니다. 임의의 첫 서비스나 서로 다른 digest를 합친 hash를 Docker digest처럼 제공하지 않습니다.
- 단일 서비스의 digest와 MSA 배열은 같지 않으므로 소비자 동일성 표도 서비스별로 비교하도록 확인합니다. 태그·커밋만으로 digest를 만들어내지 않습니다. 이 응답 형태 결정은 서버·소비자가 지금 할 수 있고 실제 digest 원본 수신만 #35 대기입니다.

### S6. 롤백

- rolled_back_from은 복원할 성공 배포 ID로, 실패를 계기로 실행한 배포는 별도 trigger 참조로 구분합니다. 초기 범위는 전체 성공 배포를 원본으로 선택하고 그 안에서 target_ids로 복원 대상을 고르는 안입니다. 부분 성공 배포의 성공 target만 원본으로 삼는 확장은 후순위입니다.
- `POST /deployments/{id}/rollback`의 id가 복원 원본인지 트리거인지 은현과 명확히 정합니다. 권장안은 원본 성공 배포 ID이며, 다른 의미를 유지해야 한다면 명시적 원본 ID 입력을 받습니다. '가장 가까운 성공'을 암묵적으로 선택하지 않습니다.
- 사용자의 reason은 길이·권한을 검증하고 제어 요청 snapshot과 생성 이벤트에 보관하는 안입니다. 실행 입력 snapshot은 원본 그대로 보존하고, reason을 Terraform 입력으로 섞지 않습니다. 기존 idempotency.response에는 요청 본문을 억지로 넣지 않습니다.
- 실행 브랜치의 현재 RollbackRequest에는 target_ids·사용자 reason이 없고 전체 원본 대상을 복제합니다. 계약 확정 후 요청 hash에 선택 대상·reason을 포함하고 관련 검증을 추가해야 합니다. 이번 ERD PR에서 동작 완료로 표시하지 않습니다.

### S7. SSE와 오류의 후속 동작

- 같은 채널과 seq를 유지한 채 event_type 선택 필터를 두는 안입니다. 필터 때문에 seq가 건너뛰어도 유실로 판단하지 않고 Last-Event-ID는 원래 채널 seq를 사용합니다. 공통 필터 구현은 실행 기능 PR에서 합니다.
- TARGET_LOCKED.retryable은 우선 false를 유지하고 상태를 새로 조회한 뒤 사용자 재시도로 안내하는 안입니다. 승인/apply의 자동 재전송을 허용하는 의미로 true를 사용하지 않습니다. 업무 서비스에서 알려진 constraint별 매핑·멱등 기존 응답 재조회, 인증 필터에서 403을 연결합니다.

### S8. 선택 필드·관리 API와 안내

- 제공 대상으로 제안: source_version_id, branch, target title, 확인된 current_commit, manifest ref, 실제 script 검증 시각·출처. '생성 시각'에 검증 시각을 이름만 바꿔 넣지 않습니다.
- 인프라 데이터 대기: 실제 image_digest, health(상태 코드·1회 ms), state_backend, 정확한 대상별 steps, 호출별 AI 사용량. API 형태는 지금 정하고 미수신 값은 명시적으로 미확인 처리합니다.
- 후순위: 표시 version(v7), commit_message/작성자/커밋 시각, script note, 비밀값 제거를 거친 raw/input. p95·리소스별 월 비용·별도 앱 버전/환경변수 hash는 현재 미제공 제안입니다.
- A-12 프로젝트 상세는 은현의 관리 API 범위에 포함하는 안, A-10 연결 테스트·A-11 실제 리소스 조회는 인프라 제공 범위 확인 전 후순위입니다. 데모 인증은 기존 /auth/token의 viewer 계정 재사용을 제안하되 발급 방식·계정 공유는 은현 결정입니다.
- 이 분류를 은현 확인 후 #13에 한 번에 답변합니다. R-08 서버 주소·오픈 시각은 준비된 후 공유하며, 이 문서로 새로운 날짜를 약속하지 않습니다.
