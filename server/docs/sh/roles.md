# 김승환 역할 — 배포 실행·신뢰성·공통 기반

기준: 2026-10-01. 현재 Jenkins 분담과 #19·#17 피드백 반영. 구현 완료 여부는 별도 명세·검증 기록을 따릅니다.

배포 요청부터 승인·실행·장애 복구까지 연결된 규칙과 이벤트·SSE 기반을 책임집니다. 인증·인가 구현은 하은현 담당이며 김승환은 제공받은 접근 권한 서비스와 연결합니다. 아래는 개발 범위와 확인 기준이며 구현 완료를 뜻하지 않습니다.

[전체 업무](../work.md) · [하은현 역할](../eh/roles.md)

## 1. 담당 업무

| 영역 | 구현할 내용 | 핵심 확인 기준 |
|---|---|---|
| 배포 실행 도메인 | 배포·대상별 실행, 커밋·입력 고정, 상태 전이, 멱등성·실행 충돌·트랜잭션 | 같은 요청의 동시 접수로 배포가 중복 생성되지 않음 |
| Jenkins 연동 | 실행·중단 요청, 큐 ID에서 Job·실행 번호로 추적, 인증된 결과 수신 | 정확한 배포·대상·실행에만 결과가 연결됨 |
| 승인·제어 규칙 | plan 식별, 승인·거절·재승인, 취소·중단, 실패 대상 재시도·새 롤백 배포 | 변경된 plan에 이전 승인이 적용되지 않음 |
| 이벤트·복구 | 중복·지연·역순 이벤트 처리, 응답 유실 확인, 재시작 후 상태 재확인 | 완료 상태가 오래된 이벤트로 되돌아가지 않음 |
| 결과 수집·기록 | 로그 수집 위치, 이벤트 저장·seq, plan·코드 참조 연결, AI 호출 원본 수신·중복 방지·저장 | 같은 결과·호출을 다시 받아도 중복 기록·집계되지 않음 |
| 실행 공통 기반 | 예외 처리, SSE 연결·재생 구조, 하은현의 인가 서비스 연결, 최소 호출 예제 | 권한 검사 우회 없음, 재연결 기준과 오류 형식 일관성 |
| 핵심 검증 | 상태·승인·동시 요청·부분 실패·통신 장애·재시작 테스트 | 실제 재현한 테스트와 설계 근거를 남김 |

실제 AI 호출·Terraform 생성·검증·실행은 인프라팀이 맡습니다. 김승환은 실행 결과를 서비스의 올바른 상태로 연결하는 부분을 구현합니다.

## 2. 하은현에게 제공할 것

- 배포 시작·승인·거절·취소·중단·재시도·롤백을 요청할 실행 서비스 계약.
- 각 요청에 필요한 사용자·프로젝트·대상·커밋·plan 식별 정보와 검증 책임.
- 반환할 배포 ID·상태 및 충돌·권한·입력 오류의 표현.
- 조회 API에 사용할 배포·대상·plan·산출물·사용량 데이터 의미.
- 실행 서비스·예외 처리·SSE 연결·재생을 사용하는 최소 예제. 인증된 사용자 식별과 프로젝트 접근 권한 검사는 하은현의 인증·인가 서비스를 사용합니다.
- Jenkins가 없어도 API 개발을 진행할 수 있는 계약 기반 샘플 응답 또는 테스트 대역.

메서드명·DTO 필드·상태 값·물리 테이블은 계약을 함께 확인한 뒤 확정합니다. 호출 예제를 제공하기 위해 별도 프레임워크나 큰 공통 라이브러리를 만들지 않습니다.

## 3. 인프라팀과 맞출 것

- 정확한 커밋·대상·배포 ID를 전달하는 Job 파라미터.
- 큐·Job·실행 번호와 서비스 배포 ID의 연결.
- 대상별 단계·plan·완료·오류·재사용·AI 사용량의 구조화된 결과.
- 승인된 plan을 지정해 실행하는 방법과 stale 재plan 처리.
- 중단 요청·실제 종료 결과·재시작 후 실행 상태 확인 방법.
- 로그의 대상 구분·비밀값 제거, 산출물 보관·만료와 조회 권한.
- 백엔드와 Jenkins 사이 통신 경로·인증·중복 실행 확인 방법.

결과 수신은 서버 폴링이며 5초는 초기 제안입니다. 현재 `daisy-cd-plan`·`daisy-cd-apply`로 분리합니다. request_id 검색·중복 방지와 구조화된 대상 결과·호출별 사용량은 연동 대기입니다. apply STOP은 미지원이며 plan stop도 실제 호출 미검증입니다. Job 설정을 바꿔도 이미 시작한 실행의 식별 정보는 보존합니다.

## 4. 직접 맡지 않는 것과 경계

- Claude 호출·Terraform CLI·AI 수정 루프·실제 CI/CD를 백엔드에 다시 구현하지 않습니다.
- 로그인·Bearer 토큰 발급/검증·계정/역할·프로젝트 인가는 하은현이 구현합니다. 실행 서비스는 인가를 생략하지 않고 해당 서비스를 사용합니다. 승인 권한은 인가 영역, 현재 plan의 승인 가능 여부는 실행 도메인입니다.
- 프로젝트·레포·대상 관리와 사용자용 조회 API는 하은현이 기능 단위로 완성합니다.
- 사용량 원본의 수신·연결은 담당하지만 조회·합산·원화 응답은 하은현의 조회 기능과 연결합니다.
- 다른 도메인의 Repository·Entity를 직접 수정하지 않습니다. 필요한 입력은 서비스 계약으로 받습니다.
- 배포 상태·승인 유효성은 실행 서비스 한 곳에서 판단합니다. API·폴링 수신부가 각자 별도 규칙을 갖지 않도록 합니다.
- 기존 은현의 코드·DDL은 먼저 확인합니다. 이동·소유 변경·Flyway 버전 배정은 협의 후 진행합니다.

## 5. 첫 개발 순서

1. 은현과 분담·기존 작업을 확인하고 실행 서비스의 요청·응답·오류를 먼저 맞춥니다.
2. 인프라 연동 초안과 예외·실행 서비스 호출 예제를 제공하고, 하은현의 인증·인가 계약과 연결해 병렬 개발합니다.
3. 한 대상의 배포 생성 → plan 수신 → 승인 → 실행 요청 → 완료 기록을 최소 흐름으로 연결합니다.
4. 동시 요청·중복 이벤트·오래된 승인·응답 유실·재시작·부분 실패를 검증하고 필요한 복구 처리를 붙입니다.

추가 기술 도입보다 기존 Spring·PostgreSQL·Jenkins로 필요한 규칙을 해결합니다. 실제 인프라 변경을 수반하는 통합 검증은 사람 확인 후 진행합니다.

## 6. 완료 판단과 검증 근거

- 핵심 흐름에 대한 실행 가능한 테스트와 실패 재현 사례가 있습니다.
- 서버 재시작 후 기존 실행을 다시 추적하며 무조건 새 실행을 요청하지 않습니다.
- 승인된 plan과 실행 대상의 동일성을 확인하고, 재plan은 새 승인을 요구합니다.
- 환경별 실패와 전체 배포 결과를 구분해 제공할 수 있습니다.
- 은현의 API가 상태를 직접 바꾸지 않고 실행 서비스를 호출해 동작합니다.
- 실제 검증한 범위와 한계를 명시합니다. DB 멱등성만으로 Jenkins 실행까지 정확히 한 번을 보장했다고 주장하지 않습니다.
