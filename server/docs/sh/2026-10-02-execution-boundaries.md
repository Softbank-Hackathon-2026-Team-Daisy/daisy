## 승환 실행부 변경

- 사용자 명령의 공통 멱등 처리에서 프로젝트 행 락을 얻을 때 archived_at을 재검사해요. 외부 결과 수신 경로는 차단하지 않아요.
- Jenkins 명령 targets[].attempt를 전달해 apply와 단순 stale replan에서 생성 횟수가 초기화되지 않게 해요. 인프라가 그 값을 이어받아야 실제 연동이 완성돼요.
- 기존 워커에서 만료 pending 승인 후보를 최대 100개 조회하고, 대상마다 별도 트랜잭션의 expire를 호출해요. 종료 미확인·approved/apply는 보존하고, 동시 승인으로 후보가 바뀌면 STATE_CONFLICT만 건너뛰어요.
- 별도 워커·큐·테이블·의존성 없이 기존 서비스와 스케줄러를 재사용했어요(Ponytail).

## 검증

Java 21, Gradle 8.14, 격리된 로컬 PostgreSQL 17에서 다음을 실행했어요.

```sh
./gradlew spotlessApply check build --rerun-tasks --no-daemon --offline
```

DB 연결은 DAISY_TEST_DB_* 환경변수로 테스트 전용 포트에 설정했고 각 테스트는 별도 스키마를 사용해요.

- 최종 215개 통과, 실패·오류·스킵 0개, BUILD SUCCESSFUL이에요.
- 최초 검증에서 등록 target ID와 deployment_target ID 혼동으로 신규 만료 테스트 2개가 실패했고, 후보·호출의 ID를 맞춘 뒤 전부 다시 통과했어요.
- 일부 만료 후 A-04 reader가 주는 남은 approval ID로 승인 성공, 전체 만료 취소·이벤트 중복 없음, 종료 미확인 보존, 이미 승인된 apply 보존을 확인했어요.
- 연결 해제가 프로젝트 락을 먼저 얻는 경합에서 배포·명령·멱등 행이 생기지 않는 것을 확인했어요.
- apply와 stale replan 명령에 기존 attempt가 들어가는 것을 확인했어요.
- 실제 Jenkins 호출·클라우드 apply/destroy는 실행하지 않았어요.
