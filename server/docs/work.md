# 백엔드 전체 업무 범위

기준: 2026-09-30 대화에서 전달받은 Jenkins 중심 실행 구조.

이 문서는 개발할 업무를 정리한 범위 초안이며 구현 완료 목록이 아닙니다. 김승환·하은현의 세부 분담과 인프라 연동 계약은 제안으로 구분하며, 담당자 합의 후 확정합니다.

역할별 안내: [김승환 — 배포 실행·신뢰성·공통 기반](sh/roles.md) · [하은현 — 인증·인가·관리·조회 API](eh/roles.md).

## 0. 역할 변경과 문서의 전제

사용자가 전달한 새 역할 경계를 기준으로 정리합니다.

| 구분 | 담당 업무 |
|---|---|
| 인프라팀 | 사용자 저장소의 코드 빌드, 이미지 생성·게시, AI 호출, Terraform 생성·검증·수정·실행, 실제 배포 |
| 백엔드팀 | 사용자 요청·승인·이력 관리, Jenkins 연동, 실행 결과를 웹·앱에 제공 |

- 백엔드는 Claude 호출·Terraform CLI 실행·AI 수정 루프를 중복 구현하지 않습니다.
- 온프레미스의 Jenkins 실행 환경과 실제 배포 대상인 온프레미스·클라우드를 구분합니다.
- 기존 plan 확인·승인 기능은 유지하는 것을 전제로 합니다. Jenkins에서 plan 생성 후 대기하고 승인된 plan을 실행하는 연결 방식은 인프라와 합의해야 합니다.
- Job 이름은 임시 이름을 설정값으로 사용하고 추후 변경할 수 있습니다. 이름이 정해질 때까지 계약 초안 작성을 기다리지 않습니다.
- 백엔드가 필요한 입력·추적 ID·단계·plan·로그·결과 형식을 먼저 제안하고 인프라팀이 구현 관점에서 검토합니다.
- 단계·plan·완료 결과는 인증된 콜백, 콘솔 로그는 Jenkins API 조회로 받는 방식이 현재 제안입니다. 아직 확정된 연동 방식은 아닙니다.
- [기존 작업 규칙](../AGENTS.md)에는 백엔드의 Terraform 직접 실행 구조가 남아 있습니다. [개발 명세](../SPEC.md)는 이번 Jenkins 연동 방향을 협의용 초안으로 반영했습니다. 기존 팀 결정 기록은 자동으로 변경하지 않으며, 역할 재합의 후 AGENTS와 공유 계약을 함께 갱신합니다.

## 1. 인증·권한

구현 담당 제안: 하은현(9/30 사용자 지시). 김승환 실행 서비스는 이 인가 서비스를 사용하며, 권한 검사를 API에만 맡겨 우회하지 않습니다.

- 웹·앱 로그인과 Bearer 토큰 발급·검증.
- 프로젝트·배포·로그·생성 코드에 대한 접근 권한 확인.
- 승인 가능한 사용자와 조회만 가능한 사용자 구분.
- 인증 실패·권한 부족 응답 처리.
- 데모 계정 준비.

GitHub 저장소 접근 권한과 서비스 로그인은 별개입니다. Jenkins 토큰은 프론트에 노출하지 않고 서버에서 관리합니다. 새로운 로그인 방식이나 GitHub App 전체 구축을 자동으로 범위에 추가하지 않습니다.

## 2. 프로젝트·저장소·배포 대상 관리

- 프로젝트 생성·목록·상세 조회.
- 프로젝트와 GitHub 저장소·기준 브랜치 연결.
- 배포 가능한 커밋이나 빌드 목록 제공.
- 프로젝트에 연결된 온프레미스·클라우드 대상 목록과 상태 제공.
- 대상 설정과 자격증명 참조값 관리.
- `deploy.yaml` 존재 여부·기본 정보 확인 및 필요한 입력 검증.

백엔드는 배포 요청에 필요한 서비스 입력을 검증합니다. Terraform 생성이나 실행 검증을 다시 구현하지 않습니다. manifest 스키마와 양쪽의 검사 책임은 인프라와 맞춥니다.

프로젝트 삭제·저장소 연결 해제·대상 삭제의 지원 범위는 별도 합의가 필요합니다. 연결 해제를 실제 인프라 삭제로 취급하지 않습니다. 지원할 경우 진행 중 실행과 기존 이력의 처리 정책도 정합니다.

## 3. 빌드·이미지 정보 관리

- 인프라가 보고한 빌드 시작·성공·실패 기록.
- 저장소·커밋과 생성된 이미지 참조 연결.
- 화면에서 선택한 버전과 실제 배포 버전이 일치하도록 기록.
- 배포 결과에 실제 사용한 커밋·이미지 표시.
- 이미지 digest를 제공받는 경우 해당 변경 불가능한 참조도 연결.

백엔드가 이미지를 직접 빌드하는 업무는 아닙니다. 빌드 결과를 Jenkins에서 받을지 별도 GitHub Actions에서 받을지는 팀 파이프라인에 맞춥니다. 둘을 무조건 동시에 구현하지 않습니다.

## 4. 배포 요청 접수

- 사용자 권한과 선택한 프로젝트·대상 확인.
- 배포할 정확한 커밋과 입력값 확정.
- 배포 ID 발급.
- 배포 전체 기록과 대상별 기록 생성.
- 버튼 연타·네트워크 재시도로 같은 요청이 중복 생성되지 않도록 처리.
- 프론트에 배포 ID와 현재 상태 반환.

배포 ID는 이후 승인·로그·결과·이력의 기준입니다. 실행 시점의 임의의 최신 커밋으로 바꾸지 않습니다. 접수 응답은 배포 성공 응답이 아닙니다.

## 5. Jenkins 실행 연동

- Jenkins 주소·Job 이름·인증정보를 설정으로 관리.
- 배포 ID·커밋·선택 대상·입력 참조 등을 전달해 실행 요청.
- Jenkins 큐 ID 기록 및 실행 시작 후 Job 이름·실행 번호 연결.
- Jenkins 연결 실패·실행 거절·시간 초과 처리.
- 백엔드 재시작 후에도 기존 실행을 찾아 추적.
- 실행 요청 응답이 유실됐을 때 이미 실행됐는지 확인 없이 재실행하지 않도록 처리.
- 백엔드에서 Jenkins에 접근할 네트워크 경로·인증·권한을 인프라와 확인.

Job 이름은 나중에 바꿀 수 있지만 이미 시작한 실행에는 당시 Job 정보가 남아 있어야 합니다. 실행 번호만으로 서로 다른 Job의 실행을 식별하지 않습니다.

기존 Postgres 작업 테이블을 유지한다면 요청 전달·복구 용도로 사용할 수 있습니다. 새 구조에서의 워커 책임을 은현과 맞추고, Jenkins 내부 실행 큐를 백엔드에 그대로 중복 구현하지 않습니다.

## 6. 단계·상태·실행 결과 수신

- 단계 시작·완료·실패 이벤트 수신.
- 배포·대상·Jenkins 실행 식별자의 연결 확인.
- 단계별 시작 시각·소요 시간·실패 원인 기록.
- 환경별 상태와 배포 전체 상태 계산.
- AWS만 실패하고 온프레미스는 성공하는 부분 실패 표현.
- AI 생성·수정 시도 횟수와 코드 재사용 여부 수신.
- 중복 이벤트, 순서가 뒤바뀐 이벤트, 이전 실행의 늦은 결과 처리.
- 통신 단절·서버 재시작 후 실제 실행 상태 재확인.
- 콜백 방식 채택 시 호출 인증·입력 검증·중복 처리 방지.

시도 횟수나 성공 여부를 콘솔 로그 문장으로 추측하지 않습니다. 인프라가 명시적으로 전달하도록 계약합니다.

기존 의미를 유지하는 제안은 최초 생성 포함 총 3회, 환경별 독립, 단순 stale 재plan은 attempt 증가 없음입니다. 재사용 경로의 attempt가 0이어도 미시작 상태와 혼동할 수 있으므로 attempt만으로 재사용 여부나 실제 AI 호출 수를 판단하지 않습니다. 이 의미도 실행 담당인 인프라에 공유합니다.

## 7. Plan 조회·승인·실행 연결

- 인프라가 보낸 생성·변경·삭제 개수, 삭제 포함 여부, 위험 목록 저장·조회.
- 승인 대기 중인 배포와 대상별 plan 제공.
- 승인·거절 요청 처리.
- 승인자·승인 시각 기록.
- 어떤 대상의 어떤 plan을 승인했는지 연결.
- 중복 승인과 승인 전 실행 방지.
- 승인된 plan을 지정해 인프라에 실행 요청.
- stale 등으로 plan이 바뀌면 새 결과를 보여주고 다시 승인받도록 처리.

백엔드는 승인 여부를 관리하고 인프라는 해당 plan을 실제로 실행합니다. plan 생성과 apply 사이의 대기·재개 방식은 백엔드가 초안을 만들어 인프라팀과 맞춥니다.

기존 `PlanSummary`의 `counts`, `has_delete`, `risks`와 비용 분리 원칙을 연동 계약에 반영합니다. 리소스 교체로 삭제가 포함되는 경우도 표시해야 합니다. 원격 실행 환경의 로컬 경로만을 승인 식별자로 삼지 않고 plan 참조·버전 또는 digest로 동일성을 연결합니다.

## 8. 로그·실시간 진행 상황

- Jenkins 로그를 읽어 해당 배포와 연결.
- 병렬 작업의 로그를 대상별로 구분할 수 있도록 인프라와 형식 합의.
- 이미 읽은 위치를 기록해 중복 수집 방지.
- 배포 로그 조회 API 제공.
- 웹·앱에 상태·단계·로그를 SSE로 전달.
- `seq`와 `Last-Event-ID`를 이용한 재연결·이벤트 재생.
- heartbeat, 연결 종료, 보관 범위 밖 재연결 처리.
- 로그·이벤트 크기와 보관 정책 정리.
- 토큰·비밀값이 사용자 로그에 노출되지 않도록 처리.

Jenkins 로그를 받아오는 부분과 저장된 이벤트를 사용자에게 보내는 SSE는 나눠 맡을 수 있습니다. 구조화된 상태 이벤트를 콘솔 로그 해석으로 대체하지 않습니다.

## 9. 생성 코드·산출물·배포 결과 조회

- 이번 배포에서 사용한 Terraform 코드 또는 코드 참조 연결.
- 생성 코드 조회와 스크립트 목록 제공.
- plan·스크립트의 버전과 해당 배포 연결.
- 재사용 여부와 재사용한 원본 스크립트 정보 제공.
- 환경별 배포 URL, 실제 배포 버전, 성공·실패 결과 제공.
- 산출물 접근 권한과 만료·삭제 후 응답 처리.

생성 코드를 PostgreSQL에 전부 저장할지, 인프라가 보관하고 백엔드는 참조만 저장할지는 새 실행 구조에 맞춰 정합니다. 이전 PostgreSQL 저장 제안을 그대로 확정하지 않고, 재사용 판단·보관 시스템을 양쪽에서 중복 구현하지 않습니다.

민감값이 들어갈 수 있는 원본 plan이나 Terraform state를 그대로 공개하는 기능은 기본 범위가 아닙니다. 코드 조회에도 비밀값 노출 방지 계약이 필요합니다.

## 10. AI 사용량·비용

- 인프라가 전달하는 실제 LLM 호출별 사용량 수집.
- 호출을 배포·대상·단계와 연결.
- 동일 호출 정보가 다시 와도 중복 집계하지 않기.
- 모델·토큰·호출 성공 여부·USD 비용 저장.
- 배포별·프로젝트별 합산과 조회.
- 합의한 고정 환율·반올림으로 원화 금액 제공.
- 적용 환율과 추정 비용임을 표시.
- 알 수 없는 사용량·비용은 0이 아니라 미확인으로 처리.

생성 시도 횟수, 실제 AI 호출 수, 코드 재사용 여부는 서로 다른 값입니다. 호출 성공 여부도 Terraform 검증 성공 여부와 구분합니다. AI 호출이 없으면 호출 기록을 가짜로 만들지 않습니다.

N-09의 백엔드 업무는 직접 LLM을 호출하면서 기록하는 것이 아니라 인프라의 호출 기록을 받아 조회·집계하는 것으로 바뀝니다. 수집할 필드와 공급자별 비용·사용량 제공 가능 여부를 인프라와 맞춥니다. USD 비용 합산 후 고정 환율로 원화 환산·반올림하는 순서는 기존 합의를 유지합니다. 환율 숫자와 상세 반올림 방식은 미결입니다.

## 11. 취소·재시도·롤백·배포 이력

- 배포 목록·상세·상태별 필터·페이지네이션.
- 누가 무엇을 요청하고 승인했는지 기록.
- apply 전 취소 요청과 실행 중 중단 요청 구분.
- 인프라에 중단 요청을 전달하고 실제 종료 결과 확인.
- 실패한 환경만 새 배포로 재시도.
- 재시도한 배포와 원본 배포 연결.
- 이전 성공 버전으로 롤백하는 새 배포 요청.
- 롤백도 새 plan·승인을 거쳐 실행.
- 중단·재시도·롤백 결과를 이력에 연결.

요청을 보냈다는 이유만으로 취소·롤백 성공으로 표시하지 않습니다. 재시도 관계는 같은 커밋·시간으로 추측하지 않고 명시적으로 연결하는 방향을 제안합니다.

롤백은 앱·인프라 배포 버전의 복원이지 DB 데이터 복구가 아닙니다. 이전 코드·이미지·입력 참조를 어떻게 복원할지 인프라와 계약하고, 과거 코드가 맞지 않으면 AI 자동 수정 없이 중단한다는 기존 방향도 공유합니다.

## 12. 공통 기반·계약·검증

- 새 구조에 맞는 ERD·Flyway 마이그레이션·엔티티.
- 데이터 중복 방지 제약과 상태 변경의 트랜잭션 처리.
- 백엔드 중복 배포 제어와 인프라의 실제 실행 락 사이 경계.
- 웹·앱용 OpenAPI와 인프라 연동용 요청·이벤트 명세.
- 공통 오류 응답, `snake_case`, UTC 시간, 멱등성 규칙.
- CORS와 `Authorization`·`Last-Event-ID` 등 필요한 헤더 지원.
- 로컬 설정·`.env.example`·기동 방법·health 확인.
- Jenkins 없이도 개발할 수 있는 샘플 응답·테스트 대역.
- 정상 배포·부분 실패·중복 요청·중복 이벤트·오래된 승인·응답 유실·재시작 핵심 테스트.
- 타 사용자 접근 차단과 인프라 콜백 인증 테스트.
- 실제 Jenkins와 웹·앱을 연결한 전체 흐름 검증.

외부 호출은 DB 트랜잭션을 오래 점유하지 않도록 분리합니다. Terraform state·실행 잠금·작업 파일의 실제 관리는 인프라팀과 경계를 맞추며, 백엔드의 중복 요청 방지만으로 실제 인프라 잠금이 대체된다고 가정하지 않습니다.

샘플·테스트 대역은 목업임을 표시합니다. 실제 인프라 생성·변경·삭제를 수반하는 검증은 사람 확인 후 진행합니다.

## 13. 후순위·선택 기능과 제외 범위

| 항목 | 취급 |
|---|---|
| 원문 plan 텍스트·상세 리소스 전체 | 기존대로 후순위 |
| APNs 푸시·기기 토큰 관리 | 선택 기능 |
| 대상 연결 테스트·상세 리소스 조회 | 기존 선택 요청으로 제공 여부 합의 |
| 추가 스크립트 메타데이터·환경변수 해시 | 웹·앱 선택 필드 요청 |
| 리소스별 월 인프라 비용 예측 | AI 비용과 별개, 기본 범위 제외 |
| apply 전 AI 에러 예측 | 백엔드 직접 구현 제외, 필요하면 인프라와 별도 협의 |

구버전의 ZIP 소스 업로드·IR 편집·카나리·통합 관측 플랫폼도 이번 범위에 자동으로 넣지 않습니다.

다음은 백엔드에서 중복 구현하지 않습니다.

- Claude 직접 호출과 프롬프트·AI 수정 루프.
- Terraform CLI 실행·plan 파싱 및 위험 규칙의 실행 로직.
- 실제 이미지 빌드·레지스트리 게시·클라우드 및 온프레미스 배포.
- 인프라팀이 맡는 코드 재사용 판단·실제 실행 파일·state 관리.

다만 서비스가 필요한 결과를 받을 수 있도록 해당 기능의 입력·출력 계약을 협의하는 일은 백엔드 범위입니다.

## 14. 김승환·하은현 분담 제안

김승환이 동의한 분담안이며, 하은현과 최종 협의 전입니다. 연결된 실행 규칙은 한 곳에서 관리하고, 공통 기반을 먼저 제공해 관리·조회 기능을 병렬로 개발하는 방향입니다.

| 영역 | 김승환: 실행 규칙·연동·기반 | 하은현: 관리·조회·사용자 API |
|---|---|---|
| 인증·공통 처리 | 실행 공통 예외, 은현의 인가 서비스 연결 | 로그인·Bearer 토큰·계정/역할·프로젝트 인가·기본 보안 설정 |
| 프로젝트·입력 | 실행에 사용할 커밋·입력 고정 규칙 | 프로젝트·레포·대상 관리, manifest 기본 입력 확인, 버전 목록 |
| 배포 실행 | 배포 생성 서비스, 상태 전이, 멱등성·실행 충돌·트랜잭션 | 사용자용 배포 요청 API에서 실행 서비스 호출 |
| Jenkins | 실행·중단 요청, 큐·실행 추적, 콜백·복구 | 연결된 실행 결과를 사용자 응답으로 제공 |
| 승인·재시도·롤백 | plan 승인 유효성·상태 변경·실행 정책 | 승인·취소·재시도·롤백 요청 API와 입력·권한 확인 |
| 로그·SSE | 로그 수집, 이벤트 저장·seq, 재생·연결 관리 기반 | 로그 조회, 공통 기반을 사용하는 SSE 엔드포인트 연결 |
| 산출물·사용량 | 원본 결과 수신·중복 방지·저장, 배포와 참조 연결 | plan·코드·이력·사용량 조회, 비용 합산·응답 변환 |
| 검증 | 상태·동시성·오래된 승인·중복 이벤트·장애 복구 테스트 | 입력·권한·필터·페이지네이션·응답 계약 테스트 |

각 담당자는 자신의 기능에 필요한 DTO·서비스·저장 처리·OpenAPI·테스트까지 맡습니다. 인증·인가는 하은현, SSE 연결·재생 기반은 김승환이 구현합니다. 승인할 권한은 인가 서비스에서, 해당 plan의 승인 가능 상태는 실행 서비스에서 검사합니다.

### 상태 변경 경계

하은현의 API는 인증된 사용자와 검증한 요청을 김승환의 실행 서비스에 전달합니다. 현재 상태에서 허용되는 동작인지, 승인한 plan이 유효한지 판단하고 배포 상태를 변경하는 책임은 실행 서비스 한 곳에 둡니다. 실행 서비스에서도 호출자의 권한과 프로젝트·대상 연결이 검증되도록 공통 인가 규칙을 적용합니다.

예를 들어 승인 API가 요청을 받으면 실행 서비스가 plan 식별·승인 가능 상태를 확인하고 승인 기록·상태 변경·실행 연결을 담당합니다. API에서 배포 상태를 직접 수정하거나 Jenkins를 별도로 호출하지 않습니다.

### 공동으로 정할 사항

- 배포·대상·Jenkins 실행 식별자와 인프라 요청·결과 계약.
- 실행 서비스가 받을 요청·반환값·오류와 사용자 API의 매핑.
- DB·마이그레이션·패키지 소유 경계와 Flyway 버전 번호.
- 소비자에게 제공할 API·이벤트와 전체 통합 테스트.

다른 담당 영역의 Repository·Entity를 직접 사용하지 않고 서비스 계약으로 연결합니다. 은현이 이미 작성한 코드·DDL은 먼저 확인하고, 소유 변경이나 이동은 함께 협의합니다. 파일·엔티티·테이블을 같은 목적으로 두 벌 만들지 않습니다.

자세한 담당 업무·인계 정보·개발 순서는 [김승환 역할](sh/roles.md), [하은현 역할](eh/roles.md)을 따릅니다. 전체 기능 범위와 선택 기능 구분은 이 문서가 기준입니다.

## 15. 다음 진행 순서와 남은 합의

1. 이 업무 범위와 새 분담을 은현과 맞춥니다.
2. 김승환이 인프라 연동·실행 서비스 계약과 최소 공통 기반을 먼저 정리합니다. Job 이름·주소는 임시 설정값으로 둡니다.
3. 인프라팀과 입력·콜백·로그·승인 후 실행·중단·산출물 보관 경계를 확인합니다.
4. `SPEC.md`의 협의용 초안을 구체화하고 ERD를 작성합니다. 기존 `AGENTS.md`는 역할·계약 합의 후 갱신하며, 계약 변경은 관련 파트에 공유합니다.
5. 김승환은 배포 한 건 생성 → 인프라 실행 요청 → plan 수신 → 승인 → apply 요청 → 완료 표시를 연결합니다. 하은현은 합의한 계약과 샘플 응답으로 프로젝트·관리·조회 API를 병렬 개발합니다.
6. 병렬 대상·부분 실패·재시도·사용량과 복구 경로를 연결하고 검증합니다.

특히 먼저 맞출 사항은 정확한 커밋·입력 고정, 실행 식별자, 대상별 이벤트 형식, 승인된 plan 식별·재개, 로그 전달, 중복·지연 결과 처리입니다. 최종 Job 이름이 미정이라는 이유로 이 초안 작성을 미루지 않습니다.

이 문서 작성만으로 구현·테스트·팀 합의가 완료된 것은 아닙니다. 기존 다른 파일은 별도 요청과 합의 없이 변경하지 않습니다.
