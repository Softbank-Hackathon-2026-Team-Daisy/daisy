# 10월 1일 Bearer 인증과 프로젝트 접근 권한

## 작업 범위

- `POST /auth/token` 으로 토큰을 발급하고 `GET /auth/me` 로 주체를 확인해요.
- `Authorization: Bearer` 를 검증하는 필터와, 컨트롤러가 주체를 받는 `@CurrentAccount` 를 추가했어요.
- 프로젝트 접근·변경 권한을 판정하는 `ProjectAccessService` 를 추가했어요. 실행 서비스도 이 서비스를 호출해요.
- 데모 계정 시딩과 웹 개발용 CORS 설정을 넣었어요.
- 업무 API·SSE·Jenkins 연동은 넣지 않았어요. 조회 엔드포인트는 후속이에요.
- 구현은 Claude Opus 5 로 했고, 검증 명령과 결과는 아래에 그대로 적었어요.

## 설계 이유

- **별도 토큰 테이블을 두지 않았어요.** `database-design.md` 5.1 에 *"별도 토큰 테이블은 기본 범위가 아니며 발급·검증 방식은 은현 소유"* 로 적혀 있어요. 서명과 만료만으로 검증해요. 테이블이 늘지 않고 서버를 재시작해도 로그인이 유지돼요.
- **역할은 토큰이 아니라 요청마다 DB 에서 다시 읽어요.** 토큰 발급 뒤에 권한이 바뀌거나 계정이 비활성화될 수 있어서예요. 토큰에는 계정 ID 와 로그인명만 담아요.
- **아이디가 없는 경우와 비밀번호가 틀린 경우를 같은 401 로 돌려줘요.** 어느 쪽인지 알려주면 계정 존재 여부가 샙니다.
- **필터에서 난 오류를 `HandlerExceptionResolver` 로 넘겨요.** `@RestControllerAdvice` 는 필터 예외를 받지 못해요. 그대로 두면 인증 실패가 공통 오류 봉투가 아니라 서버 기본 응답으로 나가요. 승환이 `2026-10-01-common.md` 「인계와 제한」에 *"인증 필터에서 발생하는 오류는 MVC 예외 처리기 밖"* 으로 남긴 부분이에요.
- **접근 여부와 변경 여부를 나눠서 판단해요.** 설계 5.3 대로 접근은 활성 membership, 변경·승인은 계정 역할로 봐요.
- **없는 프로젝트와 권한 없는 프로젝트를 둘 다 404 로 돌려줘요.** 403 으로 구분하면 그 프로젝트가 존재한다는 사실이 샙니다. 403 은 접근은 되는데 역할이 모자란 경우에만 써요. 계약 v0.3 의 403 설명인 *"읽기 전용 계정의 승인 거절"* 이 그 경우예요.
- **데모 계정 비밀번호를 코드·마이그레이션에 두지 않았어요.** 환경변수가 있을 때만 심고 BCrypt 해시만 저장해요. 환경변수가 없으면 아무것도 하지 않아요. 비밀번호를 로그에 남기지 않아요.
- **CORS 허용 origin 에 와일드카드를 쓰지 않았어요.** 환경변수로 받고 기본값은 개발용 `localhost:5173`·`5174` 예요.

## 인계와 제한

- ~~인가 판정이 아직 요청 경로에 붙지 않았어요.~~ → `GET /projects`·`GET /projects/{id}` 에 붙여서 실제 요청으로 확인했어요. 같은 날 후속 커밋이에요.
- **승환 실행 서비스가 호출할 입구는 `ProjectAccessService.requireRead/requireWrite` 예요.** API 가 검사했다는 이유로 생략하지 않는 것이 `docs/eh/roles.md` §3 의 전제예요.
- **토큰 폐기(로그아웃·강제 만료) 경로가 없어요.** 별도 토큰 테이블을 두지 않은 결과예요. 계정을 비활성화하면 다음 요청부터 막히지만, 이미 발급된 토큰을 개별로 무효화하지는 못해요. 필요해지면 테이블 추가를 다시 봐야 해요.
- **SSE 경로의 인증은 확인하지 않았어요.** 같은 필터를 타지만 스트리밍 응답에서 인증 실패를 어떻게 전달할지는 SSE 구현과 함께 봐야 해요.
- **CORS·프록시 스트리밍이 실제 터널 뒤에서 동작하는지 확인하지 않았어요.** 도메인과 개발 서버가 생긴 뒤에 확인해야 해요.
- `DAISY_AUTH_SECRET` 이 없으면 서버가 기동하지 않아요. 기본값을 두지 않았어요.
- 원격 push 와 PR 은 하지 않았어요.

## 검증 결과

- `spotlessApply build test --no-daemon` 성공. 테스트 18개(기존 11개 + 접근 권한 7개)를 통과했어요.
- **빈 PostgreSQL 17 에 띄워서 10가지를 확인했어요.**

  | | 확인한 것 | 결과 |
  |---|---|---|
  | 1 | 토큰 없이 보호 경로 | 401, 공통 오류 봉투 `{"error":{"code":"UNAUTHENTICATED",...}}` |
  | 2 | 틀린 비밀번호 | 401 |
  | 3 | 없는 계정 | 401, **2번과 같은 응답** |
  | 4 | 정상 로그인 | `access_token`·`expires_at`·`role` (snake_case) |
  | 5 | 발급 토큰으로 `/auth/me` | 200 |
  | 6 | `viewer` 계정 로그인 | `role=viewer` |
  | 7 | 서명이 변조된 토큰 | 401 |
  | 8 | `Basic` 헤더 | 401 |
  | 9 | CORS preflight (`localhost:5173`) | `authorization`·`idempotency-key` 허용, `X-Request-ID` 노출 |
  | 10 | OpenAPI | `/auth/token`·`/auth/me` 노출 |

- 접근 권한 단위 테스트 7개로 404·403 구분을 고정했어요. 없는 프로젝트, 비멤버, 철회된 멤버십, 정상 멤버, `viewer` 의 조회 허용과 변경 차단, **비멤버 `viewer` 가 403 이 아니라 404 인 것**, 역할만 보는 경로를 확인했어요.
- 비밀번호·토큰이 로그에 남지 않는 것을 기동 로그에서 확인했어요. 프레임워크·프록시의 모든 로그를 감사한 결과는 아니에요.

## 후속: 프로젝트 조회 API 에 인가 적용 (같은 날)

- `GET /projects` 는 활성 membership 이 있고 보관되지 않은 프로젝트만 돌려줘요. `GET /projects/{id}` 는 `requireRead` 를 먼저 호출해요.
- 목록은 계약의 `{ items, next_cursor }` 봉투를 쓰고, 이번 범위에서는 커서 없이 전부 돌려줘요.
- 데모 프로젝트를 시딩해요. 웹·앱이 붙어 볼 대상이 하나는 있어야 해서예요. 저장소 연결 절차가 정해지면 걷어내요.

### 실행에서 찾은 것

- **`ApplicationRunner` 의 기본 순서는 가장 마지막이에요.** `@Order` 를 안 붙인 계정 시더가 `@Order(100)` 인 프로젝트 시더보다 **나중에** 돌아서, 프로젝트 시딩이 계정 0개를 보고 그냥 끝났어요. 두 러너에 순서를 명시해서 고쳤어요(계정 50, 프로젝트 100). 테스트가 아니라 실제 기동에서 드러난 문제예요.

### 검증 결과

| | 확인한 것 | 결과 |
|---|---|---|
| P1 | owner 로 목록 | `{ items, next_cursor }`, snake_case |
| P2 | viewer 로 목록 | 조회 가능 (읽기 전용은 변경만 막아요) |
| P3 | 토큰 없이 목록 | 401 |
| P4 | 상세 | `repository_url`·`manifest_path` 포함 |
| P5 | 없는 프로젝트 | 404 |
| P6 | 멤버십 철회 뒤 | **프로젝트가 존재해도 viewer 는 404**, 목록 0건, owner 는 영향 없음 |

P6 이 404·403 구분의 실제 확인이에요. 403 이면 그 프로젝트가 존재한다는 사실이 샙니다.
