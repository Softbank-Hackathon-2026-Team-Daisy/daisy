# 10월 1일 빌드 목록 조회 (A-06)

## 작업 범위

- `GET /projects/{id}/builds?cursor=&limit=` 로 프로젝트가 받은 빌드 결과를 최근 순으로 돌려줘요. 소비자 모델은 `ios/SPEC.md` §6-7 의 `Build` 예요.
- **커서 페이지네이션을 넣었어요.** `(received_at, id)` 를 base64url 로 감싼 불투명 커서예요.
- `SourceVersion` 에 접근자를 붙이고 `SourceVersionRepository` 를 추가했어요.
- 응답 DTO `BuildResponse` 와 커서 `BuildCursor` 를 추가했어요. 상태 변환과 `image_refs` 평탄화를 순수 함수로 빼서 DB 없이 테스트해요.
- OpenAPI 가 `principal` 을 쿼리 파라미터로 노출하던 것을 고쳤어요 (아래 참고).
- 단위 테스트 10개를 추가했어요.
- 빌드 수신(`POST`)은 승환 소유라 넣지 않았어요. 조회만이에요.
- 구현은 Claude Opus 5 로 했고, 검증 명령과 결과는 아래에 그대로 적었어요.

## 설계 이유

- **A-02 와 달리 실제 커서를 넣었어요.** 대상은 프로젝트당 몇 개지만 빌드는 커밋마다 쌓여요. 설계 5.5 가 이미 `INDEX(project_id, received_at DESC, id)` 를 그 용도로 둬서 질의가 그 인덱스를 써요.
- **정렬에 `id` 를 동반 키로 넣었어요.** `received_at` 이 같은 행이 있을 수 있어서, 단일 키로 커서를 만들면 같은 시각의 행을 건너뛰거나 두 번 보여 줘요. 검사 B11 이 이걸 봐요.
- **커서를 base64url 로 감싸요.** 소비자가 안을 들여다보고 직접 만들기 시작하면 정렬 키를 바꿀 수 없어요. 암호화가 아니라 불투명하게 만드는 것일 뿐이라 비밀값을 넣지 않아요.
- **깨진 커서는 400 이에요.** 조용히 첫 페이지로 돌려보내면 사용자는 목록이 되감긴 것을 모르고 지나쳐요.
- **`limit` 이 최대값을 넘으면 400 이 아니라 깎아요.** 목록 조회가 한도 때문에 실패하지 않는 쪽이 나아요. 다만 0·음수는 요청이 잘못된 것이라 막아요.
- **다음 페이지 여부를 알려고 한 건 더 받아 봐요.** 따로 `count` 질의를 돌리지 않아요.
- **`pending` 을 `running` 으로 보내지 않아요.** 아래에 따로 적었어요.
- **`image_refs` 모양이 가정과 다르면 오류를 내지 않고 비워요.** 빌드 목록 조회가 통째로 깨지는 것보다 그 필드만 비는 쪽이 나아요.

## 소비자 enum 과 DB 가 어긋나요 — `pending` 에 자리가 없어요

승환 S1 이 *"나머지 상태도 기존 소비자 enum 을 대조하고, DB enum 을 API 에 그대로 노출하지 않는다"* 로 둬서 대조했어요.

| DB (`ck_sv_status`) | 소비자 계약 (`ios/SPEC.md` §6-7 `pipeline.status`) |
|---|---|
| `succeeded` | `success` |
| `running` | `running` |
| `failed` | `failed` |
| **`pending`** | **대응 값 없음** |

`pending` 은 "빌드 결과를 받았지만 아직 시작 전" 이에요. `running` 으로 보내면 시작하지 않은 것을 진행 중으로 표시하게 돼요. 목록에서 빼는 것도 아니에요 — 사용자는 빌드가 접수된 것을 봐야 해요.

**그래서 `queued` 를 네 번째 값으로 내보내요.** 소비자 계약에 없는 값이라 웹·앱에 알려야 해요. 받기 어렵다면 `pending` 행을 목록에 두고 `pipeline.status` 만 null 로 바꾸겠어요.

설계에 없는 값이 들어오면 꾸미지 않고 그대로 내보내요. 소비자가 모르는 값을 보는 게, 아는 값으로 둔갑한 것보다 안전해요.

## `image_refs` 모양을 가정했어요

설계 5.5 는 `image_refs` 를 *"성공 시 확정한 service별 이미지 객체"* 로만 적고 정확한 모양을 정하지 않았어요. 채우는 쪽은 승환 수신 서비스, 쓰는 쪽은 저라서 **가정한 모양을 적어 두고 확인을 받아요.**

```jsonc
{ "<서비스명>": { "image_ref": "ghcr.io/org/app:2311c0b", "image_digest": "sha256:..." } }
```

- 서비스가 하나면 `image`·`image_digest` 에 scalar 로 담아요.
- 둘 이상이면 scalar 를 null 로 두고 `images: [{service, image_ref, image_digest}]` 를 채워요. 승환 S5 의 제안 그대로예요.
- **임의의 첫 서비스를 고르거나 digest 를 합쳐 하나로 만들지 않아요.**
- 모양이 다르면 비워요. 모양이 확정되면 평탄화 함수 하나만 바뀌어요.

## 인계와 제한

- **`deployed_to[]` 는 비어 있어요.** `deployment` 모듈 소유라 그쪽 Repository 를 직접 읽지 않았어요 (설계 2장, `work.md` §14). source_version ID 로 "그걸로 배포된 대상·배포 ID·시각" 을 돌려주는 읽기 계약을 주시면 붙이겠어요. A-02 의 `current` 와 같은 이유예요.
- **`message`·`author`·`committed_at` 은 미제공이에요.** 승환 S1 이 *"원천 없는 커밋 설명·작성자·시각은 후순위"* 로 뒀어요. GitHub 을 따로 호출해 채우지 않아요.
- `#13` 의 `Build.steps[]`(W-03 단계)는 넣지 않았어요. Jenkins `daisy-ci` 가 단계별 결과를 보내기 전에는 만들 수 없고, 승환 S2 가 *"Job 단계를 대상 단계로 꾸미지 않는다"* 로 뒀어요.
- `image_refs` 의 실제 모양은 수신 서비스가 채우기 시작한 뒤 다시 봐야 해요.
- 빌드가 수천 건일 때의 커서 성능은 보지 않았어요.

## OpenAPI 가 `principal` 을 쿼리로 노출하고 있었어요

B16 을 돌리다 찾았어요. 보호 경로 **5개 전부**가 그랬어요.

```
GET /auth/me                              ['principal']
GET /projects                             ['principal']
GET /projects/{projectId}                 ['principal', 'projectId']
GET /projects/{projectId}/targets/status   ['principal', 'projectId']
GET /projects/{projectId}/builds           ['principal', 'projectId', 'cursor', 'limit']
```

`@CurrentAccount AuthPrincipal` 은 인증 필터가 넣어 둔 주체를 argument resolver 가 채우는 값이고 요청에서 받는 게 아니에요. 그런데 springdoc 은 알려진 애너테이션이 아닌 핸들러 인자를 기본적으로 쿼리 파라미터로 봐요. **소비자에게 `?principal=...` 을 보내라고 알려주는 문서였어요.**

`SpringDocUtils.getConfig().addAnnotationsToIgnore(CurrentAccount.class)` 로 숨겼어요. 정적 초기화를 쓴 것은 springdoc 이 빈 생성보다 먼저 이 설정을 읽기 때문이에요.

이슈 #13 의 완료 기준이 *"받은 건 OpenAPI(`/v3/api-docs`)에 나와 있어요"* 라서, 문서가 틀리면 계약이 틀린 것과 같아요. 검증 항목에 OpenAPI 를 넣지 않았으면 못 찾았어요.
